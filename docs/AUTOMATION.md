# Bounded automation (0.9.0)

Home has Start automation, Pause/Resume, and Stop. A second Stop remains in the header on every page. Settings contains connection details; Advanced retains Account, Intelligence, Minion Command, captures and preview controls. Preview pause is independent of automation pause.

Start discovers the installed ADB executable, connects to the configured loopback endpoint, and opens Super Snail (`com.qcplay.snail.android.na`). If BlueStacks is stopped, startup matches its configured instance to that port before launching it, with a bounded connection loop. An ambiguous/missing instance requires attention. Other emulators and non-loopback endpoints are not automatically bootstrapped. USB devices are not selected by automation.

The first input allowlist is deliberately small:

- Login: an exact Start word/button with server/version context or a bottom-of-frame Ver: footer, with the game in the foreground.
- Reward acknowledgment: exact OK with Rewards Gained or Obtain 1 body context.
- Update notice dismissal: exact Tap with explicit close notice text and maintenance/update context.
- Login recovery: a recognized login-verification/server-connection failure message in the central modal region and one exact central Retry button. Generic Retry, chat text, missing context and spending/consent prompts remain ineligible.

All targets come from current OCR regions. Pale/orange connected components propose button crops; color alone never authorizes a tap. Bounded footer/modal crops and contrast variants improve stylized text recognition. Full-frame observations alone enter account history; focused crops are not authoritative account readings. Everything runs locally using Windows OCR.

Core/Automation contains source/context/target/postcondition policy, the pure AutomationRunner, IAutomationPort and serializable RecoveryBudget. MainForm.Automation owns startup and UI controls; AdbAutomationPort supplies production capture/input coordination through injected observation and pause/device hooks. The same adapter is used by the opt-in live harness. A session is bound to one serial, checks the foreground package, reobserves before dispatch, and records an action intent before input. It observes the result up to three times for notices/rewards and ten times for login/recovery, without resending that tap. Unknown pixels and ADB success are not completion. A changed known screen, recognized Home, or an allowed explicit notice/recovery-to-login signature is required; the original context must disappear.

Pause gates new actions; a tap already dispatched may finish verification. Resume reobserves if pause interrupted a preflight. Stop cancels ADB/OCR/delays. Device changes cancel the run, closing cancels it, and update installation drains it before replacement. No second session starts while one is stopping. Startup never replays an unfinished input from the journal.

Twelve consecutive unsupported observations end the run with Needs attention; at least five seconds separates unsupported observations. A session also stops after twenty verified actions, 100 observations or ten minutes (including paused time). A limit reached during verification is an unverified outcome, not successful completion. A failed preflight never sends a tap. An unverified outcome ends the run without retry, except that a fresh explicit login-error state may schedule a separate, bounded recovery action. A failed login is never counted as verified login. Local `Automation/last-action.json` stores the latest intent/sent/verified/unverified checkpoint, not a durable queue. Session logs and observation history provide supporting evidence. Stop/crash may leave an intent or sent checkpoint; it is never assumed complete.

This is not a complete autonomous player or seven-day scheduler. It does not navigate facilities, deploy troops, collect arbitrary resources, clone, upgrade, plan events, solve challenges, spend currency, or purchase anything. Unsupported screens require manual intervention and another Start. OCR coverage remains limited and no accuracy percentage or unattended-duration claim is made.

Validation: deterministic policy fixtures are synthetic. The integration runner supports `--check-automation-recognition` with either its existing `--adb`/`--device` or `--image` inputs. It performs local OCR and writes a local report without input; imported files remain ineligible to act. Real game screenshots and OCR reports remain ignored under artifacts and must not be published.

## In-app game control

Game is a full-height live ADB image inside the GUI, refreshed at a 500 ms target cadence while visible. Actual refresh depends on screenshot latency; capture remains nonqueuing. Enable manual control to tap or drag; Android Back sends the Android Back key. Mouse coordinates map to the Android framebuffer through the exact Zoom/letterbox geometry. Black borders, stale frames older than two seconds, changed device/orientation and a foreground package other than Super Snail cannot send input. One input is in flight at a time; another needs a post-input frame. Inputs are user-directed, not additional automation policy rules, and are never retried automatically. Keyboard/text entry, audio, multi-touch and continuous video are not supported.

Enabling manual control stops/drains automation. Automation startup, leaving the Game page and update installation disable/drain manual control. Closing cancels input. Minimize / show BlueStacks operates only when one BlueStacks player window can be identified, otherwise it asks the user to minimize the intended instance manually. It does not kill the emulator. A window minimized by Snail Commander is restored on exit; PID/start-time checks prevent restoring an unrelated reused process. This is local mirroring with input forwarding, not a native BlueStacks window embedded by SetParent.
## Login recovery and scheduled monitoring

Recovery reserves are capped at three per fifteen minutes per profile/device and persist before dispatch. Cooldowns are 5, 15 and 30 seconds, followed by a fresh observation and preflight. Even a guard change after reservation can conservatively consume budget. Restart/Stop cannot erase it. Malformed or oversized ledgers fail closed; one profile session holds an exclusive lease. The latest run result and action checkpoint are audit records, never replay queues. Inputs counts represent dispatch attempts, including uncertain cancellations, not proof of game changes.

Login/Retry verification waits up to ten three-second checks. An explicit persistent login error can lead to a fresh Retry decision within the remaining budget. Unknown pixels, another foreground app/device, stale results, storage failure or cancellation cannot authorize a new input. Retry verification requires a recognized login/notice transition or Home board; an arbitrary changed dialog is insufficient.

Home monitoring requires three distinct task labels in the left board region of a fresh portrait frame, bound to live ADB/device/game package. It does not infer account identity or ingest quantities. It checks every ten seconds for supported dialogs and has the same finite session limits. No Done facility buttons or resources are clicked by Home monitoring. Native colors and two bounded horizontal font-width variants are retained; these are processing variants of one image, not independent evidence or training.

`--check-recovery` on the Windows integration runner uses rendered synthetic text and disposable storage; it never sends input. `--live-automation --adb <path> --device <serial> --output <isolated-folder>` is explicitly interactive: it waits for Android boot, opens the fixed game if necessary, and runs the production allowlist for 45 seconds before cancellation. Keep its private outputs ignored. Desktop capture availability is separate from these Android/ADB checks.
